# Corpus pipeline (backfill, schema, build-features)

Referenced from `CLAUDE.md`. Read this before touching `pscanner.corpus` — the enumerator,
backfill paths, `asset_index`, the DuckDB build-features engine, or any corpus CLI.

## Conventions
- **`closed_at` / `resolved_at` are observational close times.** `CorpusMarketsRepo.mark_complete` rewrites `corpus_markets.closed_at` to `MAX(corpus_trades.ts)` when backfill finishes; `record_resolutions` then propagates that into `market_resolutions.resolved_at`. The previous behavior (placeholder `now_ts` from the enumerator) collapsed the temporal split into a hash split — see #40. The training pipeline's `_partition_markets` (in `pscanner.ml.streaming`) sorts by `resolved_at` to assign markets to train/val/test, so meaningful `resolved_at` values are load-bearing for the split. If you ever bypass `mark_complete`, both columns become meaningless again.
- **`asset_index` table** maps `asset_id PRIMARY KEY → (condition_id, outcome_side, outcome_index)`. Built by Phase 1 of #42 and used by `subgraph_ingest._load_market_asset_ids` to know which CTF tokens to query for each market. **Populated by `walk_market` directly** via `_resolve_outcome_side_and_persist` after the binary outcome resolver succeeds — previously only the one-shot `AssetIndexRepo.backfill_from_corpus_trades` populated it, so markets walked between manual backfill runs had empty `asset_index` rows and silently broke subgraph backfill. The one-shot helper survives for emergency repair runs.
- **Corpus volume gates.** `pscanner.corpus.enumerator` applies a per-category lifetime-volume floor (`VOLUME_GATE_BY_CATEGORY_USD`): esports = $100K, all other categories = $1M (`_DEFAULT_VOLUME_GATE_USD`). Esports drops to $100K because the live volume gate that this floor was originally tuned to mirror was set there too — see #109. The retrained metrics.json includes `test_per_volume_bucket` (5 log-spaced buckets from `<250K` to `25M+`) so post-rebuild validation can tell whether the new sub-$1M esports cohort carries the same edge as the existing $1M+ cohort.
- `CorpusTradesRepo.insert_batch` silently filters out trades with `notional_usd < _NOTIONAL_FLOOR_USD` (default $10) — per-platform floors live in `pscanner.corpus.repos._NOTIONAL_FLOORS`.

## CLI surface
- `pscanner corpus backfill` / `pscanner corpus refresh` — pull closed-market trade history into the corpus DB via gamma + data REST.
- `pscanner corpus build-features [--rebuild] [--force] [--reset-scratch] [--duckdb-memory SIZE] [--duckdb-threads N]` — (re)build `training_examples` from `corpus_trades` + `market_resolutions` via the 6-stage DuckDB SQL pipeline (#131 + follow-ups #134, #137, #138). Measured pre-#138: 1h 5m wall on the 46 GB / 22.78M-trade desktop corpus, peak RSS 9.4 GB at `memory_limit=6GB`. Post-#138 should be faster (the fan-out fix nearly halved the copy_to_sqlite row count); next production rebuild will give updated numbers. Auto-runs `ANALYZE training_examples` post-swap so the ML training loader's planner has stats. `--force` overrides the in-progress sentinel if a prior run crashed; `--reset-scratch` also wipes the leftover DuckDB scratch file.
- `pscanner corpus subgraph-backfill [--api-key KEY] [--subgraph-version v1|v2|both] [--v2-subgraph-id ID] [--rpm N] [--page-size N] [--limit N]` — per-market subgraph-driven backfill. Default (`--subgraph-version both`) runs V1 then V2 in sequence. V2 path covers markets flagged `truncated_at_offset_cap=1`, resumable via `corpus_markets.onchain_processed_at`. V1 path covers markets flagged `v1_history_pending=1`, resumable via `corpus_markets.onchain_v1_processed_at`. Both paths filter server-side by `market_in` against the local `asset_index`. Free-tier API key (~100K queries/month) covers full corpus runs comfortably. Requires `$GRAPH_API_KEY` (or `--api-key`). The deprecated `--subgraph-id` flag is an alias for `--v2-subgraph-id`. Subgraph V1/V2 schema details: `docs/claude/polymarket-api.md`.
- `pscanner corpus backfill-gamma-tags [--db PATH] [--limit N] [--rpm N]` — backfill `corpus_markets.tags_json` + `categories_json` + primary `category` from gamma `/events?slug=`. Idempotent skip resumes on `tags_json = '[]'`; dead-slug 422 / None response quarantines as `tags_json = '__ERROR__'` so operators can re-run with explicit `WHERE tags_json = '__ERROR__'` filter for triage. ~95 min at default 50 RPM for the full ~4,741-event corpus.
- `pscanner corpus backfill-outcome-side [--db PATH] [--rpm N] [--limit N] [--dry-run]` — one-shot rewrite of binary markets whose `asset_index` + `corpus_trades` rows were stored as NO+NO due to the pre-#166 `_parse_trade` bug (#167). Discovers NO+NO pairs via a `GROUP BY condition_id` query on `asset_index`, fetches the correct `{token_id → YES/NO}` mapping per market via `data.get_market_slug_by_condition_id` + `gamma.get_market_by_slug`, rewrites both legs of `asset_index` plus all matching `corpus_trades` rows in one transaction. Resumable via `corpus_markets.outcome_side_backfilled_at`. Per-market index-seek via `idx_corpus_trades_market_ts`; ~1 gamma call per market at default 50 RPM (~34 min wall on the production 1,697-market queue). Run `pscanner corpus build-features --rebuild` after a successful backfill to regenerate `training_examples.label_won` from the corrected `corpus_trades.outcome_side`.

## DuckDB build-features engine (#131, #134, #137, #138)
`pscanner corpus build-features` runs a 6-stage pipeline (materialize_trades → stage1_events → stage2_wallet_aggs → stage3_market_aggs → stage4_wallet_cat → final_join → copy_to_sqlite). The final join writes a DuckDB-native intermediate; `_copy_to_sqlite` streams it to SQLite via stdlib `INSERT OR IGNORE` after DETACHing the corpus (the in-attach cross-DB INSERT path crashed with SIGBUS at scale, see #134). Logs `corpus.copy_to_sqlite.dups_dropped` if the SELECT produces duplicate keys — non-zero in this log is now a **regression signal**; post-#138 it should always be zero (the prior ~50% rate was a market_aggs LEFT JOIN missing `wallet_address`, fixed in #138). Intermediates live in `data/duckdb_spill/build_scratch.duckdb`, wiped on success/start, persisted on crash. The original monolithic CTE-chain spilled 90 GB on the production corpus; the rewrite replaces the dominant OR-chain self-join with `COUNT(*) FILTER` windows over the 10-category enum (`_KNOWN_CATEGORIES`, fail-fast guard refuses unknown categories at engine entry). Memory budget auto-bracketed by host RAM: ≥16GB→8GB, 10-16GB→6GB, 6-10GB→3GB; <6GB hosts refuse outright. **Auto-runs `ANALYZE training_examples` post-swap** so SQLite's planner has stats for downstream readers (especially `pscanner ml train`'s streaming loader — without ANALYZE the ML pre-pass takes 8× as long). `--reset-scratch` wipes leftover scratch from a prior crashed run (implies `--force` on the sentinel). At-scale regression test in `tests/slow/test_duckdb_engine_scale.py` (opt-in via `pytest -m slow`) generates 2M synthetic trades at `memory_limit=512MB` and asserts peak RSS < 2GB. **Pre-#138 measured production wall time** (desktop, 11 GB WSL2, 46 GB corpus / 22.78M trades): 1h 5m total, 9.4 GB peak RSS, 16 GB peak scratch, 15.59M training_examples rows. Per-stage: materialize_trades 22s, stage1 35s, stage2 4m 11s, stage3 84s, stage4 5m 16s, final_join 5m 23s, copy_to_sqlite 34m 12s, atomic_swap+analyze 13m 32s. **Note**: the copy_to_sqlite phase was inflated by the #138 fan-out — post-fix it processes ~half as many source rows so should drop substantially; updated numbers will land after the next production rebuild. Open follow-up #136: drop+recreate secondary indexes around `_copy_to_sqlite` for another expected 15-25 min win.

## Open follow-ups
- **`build-features` perf Path A landed (#114).** PRAGMA tuning, covering index, drop/rebuild secondary indexes, larger insert batches with bounded WAL, and structlog progress events. Most of this scaffolding has been superseded by the DuckDB engine (#131) but the covering index still benefits incidental corpus queries. **Operator note**: the first invocation of any corpus CLI after this merge will pause ~5-15 min while the 11-column covering index builds (replaces the old 4-column index in one DROP+CREATE migration); subsequent invocations return immediately. The new index adds ~3.4 GB to the on-disk corpus DB.
- **`pscanner corpus backfill` is now feature-complete on Polymarket (#115).** It runs `_register_missing_polymarket_resolutions` after the trade drain so a fresh corpus pull never lands in a feature-incomplete state. `pscanner corpus refresh` continues to do the same on its incremental sweep — the helper is shared. `build-features` also now emits `corpus.build_features_missing_resolutions` (WARN) at startup if any complete market lacks a resolution row, with the count and first 5 condition_ids in the payload. Manifold and Kalshi auto-registration is deferred — same pattern can be applied if their backfill paths grow the same surprise.
- **Drop+recreate `training_examples_v2` secondary indexes around `copy_to_sqlite`** (#136). The DuckDB engine's `_copy_to_sqlite` does row-by-row INSERTs while 3 secondary indexes are live, maintaining each index per-row. Drop before bulk insert, recreate after (matching the `TrainingExamplesRepo.drop_secondary_indexes() / recreate_secondary_indexes()` pattern from #114). Expected ~15-25 min wall savings on production (the phase was 34 min of the 65-min total pre-#138).
