# ML training pipeline (`pscanner.ml`)

Referenced from `CLAUDE.md`. Read this before touching `pscanner.ml`, `training_examples`
features, or `scripts/analyze_model.py`. The feature-build side (DuckDB engine, build-features
CLI) lives in `docs/claude/corpus.md`.

## Pipeline
- **Optimization target**: `realized_edge_metric` from `pscanner.ml.metrics` — mean of `(label_won - implied_prob)` over taken bets (where `pred > implied`). Returns `-1.0` sentinel when fewer than `n_min` bets pass the gate (default 20) so trial configs that overfit a tiny lucky subset get penalized.
- **Inner-loop early-stopping uses the edge metric directly** (#43). `_make_edge_eval_metric` builds an xgboost `custom_metric` returning `("realized_edge", -edge)` (negated so xgboost's default minimize acts as edge-maximize). The `n_min` flat region becomes `+1.0` after negation; xgboost reads it as the worst possible value and continues training rather than stopping in the plateau. `eval_metric=logloss` stays in params as a calibration sanity baseline in train logs.
- **Outer Optuna loop** maximizes `realized_edge_metric` directly via `direction="maximize"`. The two loops are now aligned — previously the inner loop optimized logloss and Optuna optimized edge, picking trials' `best_iteration` from the wrong metric.
- **Category-aware filter metadata** (#41): `accepted_categories` field on `preprocessor.json` (default `(Category.SPORTS, Category.ESPORTS)`) plus `test_edge_filtered` in `metrics.json`. Retained on the artifact for downstream consumers (model evaluation tooling, future live scoring); no live consumer exists in the daemon today.
- **Wallet-quality interaction features** (#44): four new columns on `training_examples` activate at the 70/15/15 split (per the 2026-05-06 production run):
  - `edge_confidence_weighted = realized_edge_pp * min(1, prior_resolved_buys/20)`
  - `win_rate_confidence_weighted = (win_rate - 0.5) * min(1, prior_resolved_buys/20)`
  - `is_high_quality_wallet = (prior_resolved_buys >= 20) AND (win_rate > 0.55)`
  - `bet_size_relative_to_history = bet_size_usd / median_bet_size_usd` — always 1.0 in v1 (the streaming feature provider doesn't yet maintain a running median; future v2 will)
  - At 60/20/20 (depth=3, 26 trees) these all rounded to zero gain. At 70/15/15 (depth=9, 124 trees) they appear in the top 25 by gain — `win_rate_confidence_weighted` (#14), `is_high_quality_wallet` (#18), `edge_confidence_weighted` (#22), plus `prior_losses` / `prior_resolved_buys` / `prior_wins`. The bigger train set lets the deeper booster extract wallet signal that v1 couldn't.
- **Streaming corpus load** (#39, replaced eager `load_dataset` deleted in 2026-05-06): the training pipeline reads via `pscanner.ml.streaming.open_dataset(db_path)` (context manager). Two-pass architecture — small pre-pass (split partition + encoder fit + per-split row counts via per-connection `TEMP TABLE` JOINs) at `__enter__`, then per-split chunked SELECTs feed `xgb.QuantileDMatrix(SplitDataIter(...), max_bin=256, ref=dtrain)` for train/val. Test split is materialized into pre-allocated numpy arrays via `ds.materialize_test()` for `evaluate_on_test`. **Never resurrect `load_dataset` / `temporal_split` / `Split`** — they're deleted; `open_dataset` is the canonical path.
- **Split fractions**: `_TRAIN_FRAC = 0.7`, `_VAL_FRAC = 0.15` (test = 0.15) live in `streaming.py`. Bumped from 60/20/20 in #73 because per-market activity grew ~9× from 2024 to 2026, so 60% of markets only translated to ~40% of rows. At 70/15/15 train gets ~10M rows / val ~2.5M / test ~4.9M on the production corpus. Test_edge nearly doubled vs the old split (0.015 → 0.026).
- **xgboost 3.x QuantileDMatrix(DataIter) gotchas** (discovered during #39): (1) `feature_names=` kwarg rejected when the data arg is a `DataIter` — assign `dm.feature_names = list(...)` post-construction (and only set them on matrices whose feature set matches downstream `predict()` callers — setting on `dtrain` breaks `evaluate_on_test`'s plain `xgb.DMatrix(X_test)` path). (2) `device=` is not a `QuantileDMatrix.__init__` kwarg — forward to `xgb.train(params={"device": ...})` instead. (3) The val matrix MUST be constructed with `ref=dtrain` so it shares quantile cuts; otherwise small-data tests pass coincidentally but production training diverges.
- **Build features**: `pscanner corpus build-features --rebuild` (re)builds `training_examples` from `corpus_trades` + `market_resolutions` via the DuckDB SQL pipeline. The streaming loader discovers columns dynamically via `PRAGMA table_info`, so adding new columns to the build pipeline doesn't require updating ML code.
- **Multi-label `cat_*` indicators (#122).** `training_examples` carries 9 binary columns `cat_sports`/`cat_esports`/`cat_thesis`/`cat_macro`/`cat_elections`/`cat_crypto`/`cat_geopolitics`/`cat_tech`/`cat_culture`, populated by `build-features` from `features.market_categories` (set membership). The single string `market_category` is retained on the row but no longer one-hot-encoded — the encoder reads `side` + `top_category` only; the 9 `cat_*` columns flow through as int32. `_NEVER_LOAD_COLS` now excludes `market_category` from the SELECT so the float32 conversion can't trip on it. `preprocessor.json` carries `"version": 2`. `scripts/analyze_model.py` emits a `per_category_any` breakdown over the `cat_*` columns alongside the existing wallet-level `top_category` partition (Decision E on #119).
- **Feature projection registry (#145).** `pscanner.corpus.feature_projection` is the single source of truth for the FeatureRow projection step AND for the shared dataclasses (`Trade`, `WalletState`, `MarketState`, `MarketMetadata`, `FeatureRow`) + state helpers (`apply_*_to_state`, `empty_*_state`, `compute_features`) + `StreamingHistoryProvider`. The old `pscanner.corpus.features` module was folded into this one when the live daemon gate-model stack was deleted. `FEATURES: tuple[FeatureFormula, ...]` carries one entry per `training_examples` column with both a Python lambda and a parameterized SQL fragment. `compute_features` (consumed by the corpus `StreamingHistoryProvider`) and `_duckdb_engine._final_join_to_v2` both derive their projection from this registry. Magic numbers (`CONFIDENCE_N_MIN`, `HIGH_QUALITY_WIN_RATE_THRESHOLD`, `KNOWN_CATEGORIES`) live as module constants. `tests/corpus/feature_projection_sql.snapshot` is a PR-review diff of the emitted SQL. Adding a feature: add a `FeatureFormula` entry to `FEATURES`, add a field to `FeatureRow`, regenerate the snapshot. `FeatureFormula.project_to_sql=False` marks compute-only features (e.g. `market_categories`) that exist on FeatureRow but aren't persisted to the SQLite schema.

## Training CLI
`pscanner ml train --device cuda --n-jobs 1 [--chunk-size 100000] [--n-trials 100]` runs xgboost training. `--n-jobs 1` is required on GPU — parallel Optuna trials would compete for the 8 GB VRAM. **Wall time scales with corpus row count.** 2026-05-06 baseline (~10M rows, 100 trials, 70/15/15): ~42 min total on the desktop (RTX 3070). 2026-05-15 (15.6M rows post-DuckDB-rebuild): 1h 18m total (~2 min pre-pass / ~37 min DMatrix / ~28 min Optuna / ~11 min finalize), peak RSS ~3.8 GB at `post_dmatrix`. **`ANALYZE training_examples` is load-bearing**: the DuckDB engine runs it automatically post-swap (#131 follow-up); without stats, the pre-pass jumps from 2 min to 16 min and DMatrix construction from ~12 min baseline to ~37 min. The post-#39 streaming pipeline survives the laptop's 7.6 GB constraint by never materializing the full corpus into Polars (was 11.8 GB anon-rss → OOM under the eager loader). `--chunk-size` defaults to 100_000; tuning it UP is anti-pattern — empirically slower AND uses the same RSS at the WSL2 page-cache scale. See `LOCAL_NOTES.md` (gitignored) for the desktop training-box workflow.

## Production baselines
- **2026-05-06 (100 trials, 70/15/15)**: test_rows=4.89M, test_edge=0.026 (overall), test_edge_filtered=0.069 (sports+esports), test_AUC=0.93. Per-category: sports +6.9%, esports +10.7%, thesis +1.6% (flipped from −1% at 60/20/20), (none) +0.4%. Top decile carries +3-10% edge. Wall time ~42 min on the desktop's RTX 3070; peak host RSS ~3 GB at `post_dmatrix`.
- **2026-05-15 (100 trials, 70/15/15, first run on the DuckDB-engine corpus)**: training rows 15.59M, best_iteration=27 (vs prior 124 — shallower, faster booster), max_depth=9, test_edge=0.030 (overall), best_val_edge=0.065, test_accuracy=0.852, test_logloss=0.297. Per-decile mean_edge shows the long-shot signal: 0.2-0.3 bucket +8.3% (n=128K), 0.7-0.8 +8.1% (n=140K), 0.8-0.9 +5.1% (n=254K), 0.9-1.0 +3.2% (n=814K). Wall time 1h 18m post-ANALYZE on the desktop's RTX 3070 (15.6M rows vs prior 10M); peak RSS ~3.8 GB. The corpus this trained on was rebuilt by the pre-#138 DuckDB engine which had a ~2× fan-out bug at the market_aggs LEFT JOIN; `INSERT OR IGNORE` deduped at write time so the resolved training_examples is correct, but the rebuild wasted compute on the dups. Post-#138 rebuilds should produce identical model results in less wall time.

## Open follow-ups & tracked work
- **ML pipeline platform filter.** `pscanner ml train --platform <name>` filters training to a single platform (default `polymarket`); the streaming `open_dataset` threads the parameter through `_partition_markets`, `_fit_encoder_on_train`, `_count_split_rows`, and `_SplitIter` (whose JOIN to `market_resolutions` uses the composite `(platform, condition_id)` key). Single-platform per run by design; multi-platform aggregation (`--platform all` or comma-sep subset) is the next follow-up — the SQL idioms and parameter shape preserve forward compat (widen `platform: str` to `tuple[str, ...]`, swap `=` for `IN`).
- **SHAP sampling** (#76). `analyze_model.py`'s `_print_shap_importance` calls `booster.predict(dtest, pred_contribs=True)` over the full test split. At depth=9 / 124 trees / ~5M test rows that's hours of CPU; use `booster.get_score(importance_type="gain")` as a proxy until a `--shap-sample` flag lands.
- **`scripts/analyze_model.py` symbolic feature names**: gain-importance ranking shows `f17` / `f20` / etc. because the QuantileDMatrix construction in #39 doesn't pass feature_names to the booster (xgboost rejects it on iter-constructed DMatrix). Remap `fN → feature_cols[N]` post-hoc so the script's output is self-explanatory.
