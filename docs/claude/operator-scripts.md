# Operator scripts (`scripts/*.py`)

Referenced from `CLAUDE.md`. Read this before running or modifying anything in `scripts/`,
or when doing wallet/copy-trading research.

Single-use research / ops tools. Most are DuckDB-backed for speed (use `ATTACH '...' AS s (TYPE sqlite)` — same pattern as `_duckdb_engine.py`; ~93× faster than native SQLite for non-trivial GROUP BY / window queries, validated on the leaderboard rewrite).

- **`oneshot_resolve_paper_trades.py`** — one-shot recovery for daemons that ran before the PaperResolver predicate fix (#170 follow-up). Refreshes `market_cache` for every distinct open-position `condition_id`, then books exits via the resolver's own `_check_resolution` + `_compute_payout` helpers. Supports `--dry-run`. Used 2026-05-25 on the desktop to book 2,965 exits across 14,501 stuck positions.
- **`backfill_paper_trade_metadata.py`** — one-shot complement to `PaperTradesMetadataCollector`. Walks paper_trades condition_ids, refreshes `market_cache` (slug then token-id fallback), then refreshes `event_tag_cache`. Use to bootstrap a daemon that's been running pre-collector or post-DB-reset.
- **`analyze_copy_trading.py`** — subgraph_copy portfolio report: headline aggregates, top-N wallet exposure with HHI, top-N market exposure, per-category PnL via event_tag_cache, delay distribution, concentration warnings. Surfaces "what am I exposed to" for the current open book.
- **`analyze_wallets.py`** — per-wallet trades / wins / losses / PnL across all detectors. Sortable via `--by {trades, pnl, roi, wins, losses, win_rate}`. Cheap aggregate query against `paper_trades`.
- **`compare_wallet_cohorts.py`** — side-by-side metrics for the top-N vs bottom-N paper-trade-PnL wallets in a detector. Surfaces structural differences (outcome-side bias, category mix, market overlap via Jaccard). Validated 2026-05-25 finding: top sports cohort 61% YES / 79% sports; bottom 19% YES / 66% geopolitics.
- **`check_polymarket_wallet_pnl.py`** — pulls on-chain settled-position PnL for top/bottom paper-trade cohorts via `DataClient.get_settled_positions` (paginated `/v1/closed-positions`). Cross-check before trusting paper-trade rankings — **paper PnL ≠ on-chain cash PnL** because uniform $/trade sizing decorrelates from these wallets' actual position sizing. Top wallets by paper PnL routinely show 70%+ win rate yet 6-figure cash losses on chain.
- **`audit_watchlist_candidates.py`** — parses `watchlist_candidates.txt`, samples N wallets per section, queries on-chain settled positions, and breaks PnL down by category via `event_tag_cache`. Reports whether each flagged wallet's "flagged category" matches their best on-chain category by PnL.
- **`wallet_edge_leaderboard.py`** — DuckDB single-pass leaderboard over `training_examples`. Computes per-(wallet, category) `mean(label_won - implied_prob_at_buy)` with HAVING-based recency filter (per-wallet stats are LIFETIME counts; recency filters out inactive wallets, NOT individual trades). `QUALIFY ROW_NUMBER() OVER (PARTITION BY top_category ORDER BY edge_in_window DESC) <= ?` does per-category top-N in one query. **The `edge` metric is NOT cash PnL** — see `check_polymarket_wallet_pnl.py` for the reality check. Full 8-category sweep at limit=200/category runs in ~17s on the production 16M-row corpus.
- **`regen_watchlist_candidates.py`** — replays the curated `watchlist_candidates.txt` structure (per-category sections, drop annotations) against the post-#167 corpus via the leaderboard. Auto-applies the `lt_edge < -0.30` drop filter; the original file's `SELL ratio >= 70%` and `top_event >= 85%` filters require per-wallet `/activity` spot-checks and are NOT automated. 2026-05-25 regen produced only 35% overlap with the 2026-05-20 file — the bug-driven inversion (pre-#167 NO+NO labels) had completely scrambled the sports/esports rankings.
- **`expand_cluster.py`** — cluster expansion via fingerprint matching. Fetches each seed's recent trades on-demand via `DataClient.get_activity` (PR 4 moved this off the deleted `wallet_trades` table). The `hi_price_rate` field in the output is sampled from the seed-overlap window only — for true behavioral fingerprint, fetch `/positions?user=X&closed=true` and inspect `avg_price` distribution.

## Open follow-ups
- **`wallet_edge_leaderboard` edge ≠ on-chain cash PnL.** The leaderboard's `mean(label_won - implied_prob_at_buy)` metric rewards directional accuracy but ignores position sizing. Validated 2026-05-25: top sports-edge wallets per the leaderboard had $370K aggregate cash LOSS on chain; bottom cohort had $287K loss; both heavily negative. Selecting copy seeds purely by leaderboard edge mis-prioritizes high-volume market-makers who lose money in $ even with high per-trade "edge". Better seed-quality signal: volume-weighted cash PnL via `check_polymarket_wallet_pnl.py`. Open: should the leaderboard query incorporate a cash-PnL filter (e.g. drop wallets whose latest-100-positions cash_pnl is negative)?
- **`wallet_edge_leaderboard` `--recency-days` is a wallet-eligibility filter, not a trade-window filter.** The HAVING clause uses `MAX(trade_ts) >= cutoff` so per-wallet stats are LIFETIME counts. The docstring still says "windowed" — misleading. Either rewrite the docstring or switch to genuine windowing (`WHERE trade_ts >= cutoff` in the inner query); the latter shifts semantics meaningfully and would re-shuffle the leaderboard.
