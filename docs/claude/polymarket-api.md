# Polymarket API quirks (will bite you)

Referenced from `CLAUDE.md`. Read this before touching `pscanner.poly` clients, the daemon's
market-cache refresh paths, or anything that calls the gamma / data / leaderboard / subgraph APIs.

- **Settled positions: use `DataClient.get_settled_positions(addr)`.** Walks `/v1/closed-positions` paginated (`offset=0,50,100,…` until short/empty page). Returns wins AND losses; server caps each page at 50 rows regardless of `limit`. **Do NOT use `/positions?closed=true`** — the `closed` flag is silently ignored and the endpoint returns currently-open positions (verified 2026-05-25 against multiple leaderboard wallets).
- **Resolved markets keep `active=True closed=True` with definitive `[1.0, 0.0]` / `[0.0, 1.0]` prices.** Polymarket's gamma `/markets` does NOT flip `active=false` when a market resolves — `active` remains True forever. Predicates that gate on `cached.active=False` will never fire (this was the original misdiagnosis on #170). The reliable resolution signal is `outcome_prices == [1.0, 0.0] | [0.0, 1.0]` (prices clamp to the open `(0, 1)` interval on tradeable markets, so the boundary is uniquely a resolution marker). `pscanner.strategies.paper_resolver._is_resolved` (a `TypeGuard[CachedMarket]`) is the canonical check.
- **`gamma /markets?slug=` returns empty list for many recurring / date-rolled markets** (Iran-themed, MicroStrategy/Bitcoin variants, "by <date>" series). Slug-based refresh fails silently for that class. Use the token-id path (`gamma.list_markets(clob_token_ids=asset_id, limit=5)`) as a fallback — it returns the market WITH the `events: [...]` nesting that `_hoist_event_fields` uses to populate `event_slug`. Helpers in `pscanner.strategies.market_cache_refresh`: `refresh_market_cache_row` (slug-based, for `condition_id`-only callers) and `refresh_market_cache_by_asset_id` (token-id, for callers with an `AssetId`).
- **`Position.won = (realized_pnl > 0) OR redeemable`**, NOT a check on `cash_pnl > 0`. A wallet can show `won=True` on every settled position (Position.redeemable=True means the position-side won) yet have catastrophically negative `cash_pnl` — high-volume market-makers who provide liquidity on both sides at tight spreads lose money even when their "winning" side resolves. Validated 2026-05-25 on watchlist sports wallets showing $2.4M / $805K cash losses across 21–51 positions all flagged `won=yes`.
- Leaderboard lives at `https://lb-api.polymarket.com/profit` (NOT data-api). Window values are `1d`/`7d`/`all` — not `day`/`week`.
- Closed-position payloads expose `eventSlug`, NOT numeric `eventId`. The `event_tag_cache.event_id` column actually stores slugs (legacy name).
- `gamma /markets` does NOT return `event_id`. Backfill via `MarketCacheRepo.get(market_id)` which has it from the `/events` path.
- `gamma /events/{id}` returns 422 for slugs — use `GammaClient.get_event_by_slug` when only slug is known.
- Default `gamma_rpm = 50`, `data_rpm = 50`. Cold-start bottleneck: events catalog sweep is the main gamma consumer.
- `/trades` and `/activity` REST cap at `offset=3000` (server: `"max historical activity offset of 3000 exceeded"`, newest-first sort). The subgraph backfill (`pscanner corpus subgraph-backfill`) fills the gap.
- **Subgraph backfill.** `pscanner corpus subgraph-backfill` queries Polymarket's Orderbook subgraph on The Graph. PR #151 swapped in the current V2 subgraph (`B9mm21DKCex8ka4g8cteQU4NQqtviwmcTjQAYLbzQ1eR`) after the prior `7fu2DWYK...` indexer stopped emitting `OrderFilledEvent` rows on 2026-04-28. Both the `Exchange` and `NegRiskExchange` contracts write into the same `OrderFilledEvent` entity, so neg-risk markets are auto-covered. The decoder (`pscanner.poly.onchain.decode_order_filled`) and `AssetIndexRepo` survive — they're still useful for low-level event inspection. **V2 schema notes:** the V2 schema collapses `makerAssetId` / `takerAssetId` into `tokenId` (= `Market.id`) + `side` (Int 0=BUY / 1=SELL); the parser derives the asset-id pair from `tokenId` + `side`. `makerAmountFilled` / `takerAmountFilled` flow through unchanged. Filter via `market_in: [<asset_ids>]` (one query covers maker + taker sides). Subgraph stores `timestamp` directly. The old subgraph's earliest event was `1744013119` (2025-04-07). Live validation: the 2026-05-05 run inserted 15.87M trade rows across 2,528 markets in 10h 30m on the old subgraph. **V2 date coverage:** the current `B9mm...` subgraph (Polymarket V2 contract) only indexes events from `1775220779` (2026-04-03) onward. The 2026-05-26 run on the V2 path inserted 875,305 trades across 228 markets out of 552 attempted (41% hit rate post-`asset_index` repair). **V1 subgraph (pre-2026-04-03 history — SHIPPED in #193):** Markets that traded before the V2 start have history in the V1 subgraph (`7fu2DWYK...`). The V1 subgraph was NOT re-pushed with a different schema — Stage 0 investigation (commit `e430e54`) confirmed it still serves the pre-#151 `OrderFilledEvent` shape with flat `makerAssetId` / `takerAssetId` fields and the same `makerAmountFilled` / `takerAmountFilled` amount fields as V2. V1 and V2 index different Polygon Exchange contracts and share NO transactions — the April 3-28 2026 "overlap window" is temporal-only (verified Task 2, commit `c8c726a`). The V1 adapter ships as `pscanner.corpus.subgraph_ingest_v1`; the `pscanner.corpus.subgraph_dispatch` module routes requests to V1 / V2 / both. Sentinel: `corpus_markets.onchain_v1_processed_at` (separate from V2's `onchain_processed_at` so the two paths don't clobber each other). `corpus_markets.v1_history_pending=1` identifies the work queue (2,769 markets on the production corpus: 2,689 pure-V1 + 80 hybrid). Default invocation `pscanner corpus subgraph-backfill` now runs BOTH V1 and V2 in sequence. Use `--subgraph-version v1|v2|both` to restrict. The old `--subgraph-id` flag is deprecated (alias for `--v2-subgraph-id`).
